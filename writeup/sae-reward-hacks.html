Setup

Terminal Wrench (Bercovich et al., 2026) [4] is a public dataset of terminal tasks whose verifiers can be gamed, with 3,632 runs in which Claude Opus 4.6, GPT-5.4 or Gemini 3.1 Pro was told to make the verifier pass without doing the real work (GitHub release). Each run is a trace: one model's whole run on one task. In total there are 3,632 traces on 323 tasks. A task's traces can come from different models or from the same model trying again. Each trace splits into steps: one turn's message and commands, without their output (19,432 steps). An SAE feature is one of the Qwen-Scope layer-11 SAE's 32,768 directions. AI.SAE_FEATURES gives each document a strength per feature, after pooling over the document's tokens.

Part 1. Clustering on traces

Pool by max over the whole trace

To get one vector per trace, each feature's strength is its maximum over all the trace's tokens. Tillman and Mossing (2025) found that max-pooled SAE features make better probes than raw activations, agreeing with Bricken et al. (2024) [1]. Last-token pooling is not used here.

1[maxt at,j > 0] = 1  ⇔  j ∈ S1 ∪ … ∪ ST

Max pooling and then binarizing (next section) keeps feature j exactly when it fires on at least one token, so a trace becomes the union of the feature sets St active on each of its T tokens.

Binarize

Binarizing replaces each strength with 1 if it is above 0, else 0, so a trace becomes the set of features that fired anywhere in it. The logic: we are looking for which topics are present in a trace, not how strongly each one shows up, so presence is all we keep. Qwen-Scope does the same before picking features (Eq. 13, threshold 0) [2].

  • For: Gallifant et al. (2025) found binarized SAE features matched or beat other feature selections at lower cost [3]. Binary vectors also ignore differences in scale between features, so one feature with large strengths can't dominate the distances.
  • Against: two things are lost. First, how strongly a topic shows up: a feature that barely fires counts the same as one that fires strongly (Gallifant et al. find this can hurt in some settings). Second, with max pooling a feature counts as present if it fires on even one token, so a longer trace collects more features just by being longer.

K-Means on the binary vectors, with IDF, and with IDF top 5

Three techniques, all K-Means with k = 25 on all 3,632 traces. The choice of 25 is arbitrary; we did not tune or sweep k.

  • Binary: K-Means on the 0/1 vectors as they are.
  • Binary × IDF: first multiply each feature by its inverse document frequency, log(3,632 / traces it fires on), then divide each trace's vector v by its Euclidean length, so that ‖v‖₂ = 1. A feature that fires on almost every trace gets a weight near 0, so rarer features decide the clusters. For example, a feature on 3,000 traces gets log(3,632 / 3,000) = 0.19, and one on 100 traces gets log(3,632 / 100) = 3.59.
  • Binary × IDF, top 5: after the IDF weighting, each trace keeps only its 5 highest-weighted features, which are the 5 rarest features it fires, and those are set back to 1. Every trace then has exactly five 1s.

Lessons/Problems

  • Overall, these clusters aren't good. The best technique, binary × IDF, scores 0.58 with 20 pairs per cluster, barely over chance (0.5) and only 0.06 above a random split (0.52). The judge can rarely tell a cluster's traces from other hacks.
  • Max pooling turns on too many features. With 18,237 of 32,768 = 56% of features on in the median trace, the binary vectors mostly measure how long the trace is. Most of these features come from the parts of the trace around the exploit (reading files, planning, setting up), so they may have nothing to do with the type of hack.
  • IDF makes each trace lean on its own rare features, so traces stop sharing features. A trace's rarest features usually belong to its own task. So 11 of the 25 binary × IDF clusters each hold a single task, and many other traces end up in one 726-trace cluster that the judge scores 0.10. Keeping only each trace's top 5 makes this worse: only 1.8% of trace pairs share even one feature, one cluster takes 2,281 traces, and the judge scores 0.49 (chance).

Could it be that 6 pairs are too few?

Maybe 6 pairs per cluster is too small a sample to measure accuracy reliably. To check, we reran the judge with up to 20 pairs per cluster: the same 3 references and first 6 pairs, plus 14 new pairs, for 1,559 pairs in all.

Table 1b. The same clusters and judge, rerun with up to 20 pairs per cluster (median 20). The 6-pair column is the first 6 of those pairs, scored in the same run, so it can differ from Table 1 by 0.01.

Takeaways

  • More pairs didn't change anything. Every technique's average moved by about 0.03 at most, and the clusters are still barely above chance. The low accuracy is not from too few pairs.

Solving too many features: last token instead of max pooling

Max pooling turns on about 18,000 features per trace. The other option in AI.SAE_FEATURES is last-token pooling: keep only the features on the trace's final token, which comes after the question "How did the agent get the task to pass?". The SAE keeps exactly 100 features per token, so every trace has 100 features, and length can no longer drive the clusters. We ran the same three techniques on these vectors (k = 25, 6 pairs per cluster).

Table 1c. Judge accuracy on last-token clusters, 6 pairs per cluster.

Takeaways

  • Last token is no better: every technique is at chance. Binary scores 0.55, binary × IDF 0.49 and top 5 0.51, against 0.52 for a random split. With max pooling, binary × IDF reached 0.61 (Table 1).
  • The clusters sort traces by model, not by hack. In a typical binary or binary × IDF cluster, 0.91 or 0.90 of the traces come from one model (the models are Claude Opus 4.6, GPT-5.4 and Gemini 3.1 Pro), against 0.41 for a random split; 10 of the 25 binary clusters are at least 95% one model. With max pooling this was 0.78 and 0.70. For example, among the binary clusters:
    • cluster 4: 213 traces from 100 tasks, all Opus;
    • cluster 20: 205 traces from 100 tasks, all Opus;
    • cluster 6: 135 traces from 83 tasks, all GPT-5.4;
    • cluster 10: 163 traces from 97 tasks, 99% Gemini.

Is using full traces contaminating the features? Only the exploit steps

Maybe the problem is two mismatches:

  1. Both poolings mix in all the non-exploit steps of the trace (reading files, planning, setting up), so many extra features fire that have nothing to do with the hack.
  2. The judge only sees each trace's exploit steps, so the clusters should be built from the same text to compare like with like.

So we built each trace's vector from its exploit steps alone. Each step was already run through AI.SAE_FEATURES on its own (max over the step's tokens, top 100 kept, as in Part 2). A trace's vector is the union of its exploit steps' features, with the same binarizing as before, so a median trace has 153 features. The 28 traces with no exploit step are left out, leaving 3,604. Same three techniques, k = 25, 6 pairs per cluster.

Table 1d. Judge accuracy on exploit-step clusters, 6 pairs per cluster.

Takeaways

  • Exploit steps alone are also at chance. Binary scores 0.55, binary × IDF 0.53 and top 5 0.51, against 0.52 for a random split. So mixing in the rest of the trace was not the main problem: the SAE features of the exploit steps themselves don't group traces by hack, at least under K-Means.

Summary of strategies

  • We tried max pooling → 20 judge pairs (to rule out a small sample) → last token (to remove the extra features) → exploit steps only (to cluster the same text the judge reads), each with binary, binary × IDF and top 5 K-Means.
  • Results: the best average judge accuracy was 0.61 (max pooling, binary × IDF), 0.58 with 20 pairs, against 0.52 for a random split; max-pooled binary scored 0.59, and every other setup was at chance. The clusters follow trace length and task (max pooling) or source model (last token and exploit steps), not the type of hack.

Skip clustering: each feature is a topic

SAE features should fundamentally represent one concept each: the SAE is trained so that every feature stands for a single thing the model picks up on, such as an action, a phrase or a kind of reasoning. So why cluster at all? If that holds, one SAE feature = one cluster: the exploit steps the feature fires on. We used the step vectors from Part 2 (each step's top 100 features) and ranked features by lift:

lift = ((exploit steps it fires on + 1) / (8,724 + 2)) ÷ ((non-exploit steps it fires on + 1) / (10,708 + 2))

The +1 and +2 keep a feature that never fires on a non-exploit step from dividing by zero. Unlike Part 2's difference Δ, lift favors specific features: feature #19935 fires on 109 exploit steps and 1 non-exploit step, so its lift is (110 / 8,726) ÷ (2 / 10,710) = 67.5. We kept features that fire on 30 to 500 exploit steps from at least 10 tasks with all three models, skipped near-duplicates (more than half their steps shared with a kept feature), and judged the top 15 with 20 pairs each. The judge test is the same as before, but on single exploit steps: 3 reference steps the feature fires on, then pairs of another such step and a random exploit step it doesn't fire on. The control is 15 random groups of exploit steps of the same sizes.

What the judge misses

  • The result so far. The 15 features average 0.61 ± 0.04 against 0.51 ± 0.02 for random groups; the best clustering was 0.58 against 0.52.
  • The judge rewards wording more than tricks. The two top scores are a status phrase (#10139, 0.86) and GPT-5.4's style (#17191, 0.85).
  • Random outsiders are often the same broad trick. On #19935 (fake a package install, 0.53) the judge was confidently wrong 9 of 20 times: the outsiders were also fakes, such as a fake pytest module or an interposed sudo. A low score can mean a narrow slice of a common trick, not noise.

Potential metrics

  • Potential metric: matched outsiders. Draw each outsider from the same model and task as the member, so shared wording or task text can't pick the answer. This removes the style wins, but needs features that fire across several models within a task.
  • Potential metric: describe, then detect. An LLM writes one sentence for the feature from 5 of its steps; a judge then labels held-out steps as matching it or not, and we report precision and recall against where the feature actually fires (the "detection" score used to grade SAE feature descriptions). This tests whether the topic is specific and nameable, but depends on the describer.
  • Potential metric: agreement with the paper. Category lift, as in the panels: wrap, patch and fake-tool features carry binary-hijacking at 5–6× its base rate. This is free and uses expert labels, but the paper's 11 categories are broad and overlap.
  • Potential metric: spread. The share of a feature's steps in its top 3 tasks and from its largest model; a general trick should be low on both. #2044 fails this (61% of its steps in 3 tasks), #8283 passes (14%). This flags task families and style markers, but says nothing about coherence.
  • Potential metric: a small human check. Label 20 steps per feature as "does the named trick" or not. It is the most trustworthy, and at 15 features about 300 labels.

Part 2. Classifying exploit vs non-exploit steps

Part 2 works on single steps instead of whole traces. First, AI.FILTER with Qwen3-32B labels each step: an exploit step is one where the agent games the verifier (8,724 steps), and the rest are non-exploit steps (10,708). Then each step goes through AI.SAE_FEATURES on its own: max over the step's tokens, keeping its 100 strongest features. After binarizing, a feature fires on a step only if it is among that step's top 100. This is the "fires on" that the Δ formula below counts.

Rank features by fire-rate difference

Following Qwen-Scope (Eq. 14) [2], each feature gets

Δ = (exploit steps it fires on / 8,724) − (non-exploit steps it fires on / 10,708)

where a feature fires on a step if it is in that step's top 100. The features with the largest Δ are kept. Figure 3 shows the top 10. The names are mine, from reading each feature's 5 strongest exploit steps.

  • The top features are common and broad. The top one fires on 72% of exploit steps and 38% of non-exploit steps. Subtracting rates favors features that are frequent in both sets; a feature on 3% vs 0.1% of steps can't reach a large Δ.

Use the top K features as a classifier

Qwen-Scope's rule (Eq. 15) flags a step when any of the top K features fires on it. The features were picked on half the tasks (161 tasks) and the rule was scored on the other half: 9,166 steps, 4,190 of them exploit.

  • The classifier is weak. The best F1 is 0.70 with 2 features, against 0.63 for flagging every step. More features raise recall but flag nearly every step. Qwen-Scope reports F1 above 0.90 for toxicity; "is this step gaming the verifier" is subtler, and its labels come from another LLM.

Metrics: what we learned

  • Judge accuracy, averaged over clusters, is too blunt. Every setup lands between 0.49 and 0.61, so the average can't separate techniques. Report it per cluster instead, with 20 or more pairs: a cluster's standard error is about 0.18 with 6 pairs and 0.10 with 20.
  • Check what a high score is really about. A cluster can pass the judge by sharing a model or a task rather than a hack (max-pooling binary #4 scores 0.94 but is 95% Gemini). Report each cluster's largest-model share (0.41 for a random split) and task count, and only count clusters that mix models and span many tasks.
  • Make the judge's test harder. The outsider is a random trace today, so the judge only checks that a cluster differs from a random hack. Drawing the outsider from the nearest cluster would test whether clusters differ from each other.
  • Compare with the paper through category lift. For each cluster, the share of traces carrying a Terminal Wrench category divided by that category's share overall. Exploit-steps binary #15 has structural-extraction at 4.9×; Table 1e reads this way. A useful technique should give clusters with high lift for one category (recovery), several clusters inside one broad category (refinement), or coherent clusters with no high lift (possibly new).
  • Part 2: precision, recall and F1 against the AI.FILTER tags on held-out tasks, with F1 = 2 × precision × recall / (precision + recall).
